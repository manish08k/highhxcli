# The HighhX Computer Runtime

Native desktop observation and control — screenshots, applications, windows, the accessibility
tree, pointer, keyboard, menus, the clipboard — owned by HighhX and connected to its planner,
agent, approvals, audit and CLI. Its design was informed by [Cua](https://github.com/trycua/cua)
(MIT); no Cua code is vendored or depended on (see [Cua mapping](#cua-mapping) and
[Licensing](#licensing)).

```text
request ─ NLP / HXIR ─ planner ─ plan runner ─ ActionExecutor ──┐   HighhX Free (computer.* actions)
agent ─ computer_observe / computer_act ─ ActionExecutor ───────┤   HighhX Pro  (actor = agent)
highhx computer … ─ ActionExecutor ─────────────────────────────┤   the CLI
                                                                ▼
                               classify · approve · audit · verify (the action's own check)
                                                                ▼
                    HighhXDriver   (highhx.computer.driver — the Python API)
                                                                ▼
                    AutomationBridge   protocol v2 · argument validation · terminal guard
                          │                                  │
                  C#/.NET engine (protocol 1)      built-in engine: platform backends
                  when installed                   macOS · Windows · Linux  (native OS APIs)
                          └──────── newer operations ───────►┘
```

Browser automation (DevTools) is a separate, existing path; the desktop runtime does not
replace it.

## The Python API

```python
from highhx.computer import HighhXDriver

with HighhXDriver.create() as driver:            # target="local"; the configured engine
    state = driver.observe(screenshot=False)      # active app and window, windows, accessibility tree
    driver.press_element("Save", role="button")   # semantic: by accessible name
    driver.click(640, 400, count=2)               # at a desktop point (double click)
    driver.type_text("hello")
    driver.hotkey("cmd+s")
    driver.invoke_menu("TextEdit", "File > Save")
    driver.set_window_frame(driver.windows("TextEdit")[0].id, 0, 25, 1200, 800)
```

Other methods: `capabilities()`, `screen()`, `screenshot(window=None)`, `apps()`,
`windows(app)`, `active()`, `get_ui_tree(app)`, `element_at(x, y)`, `cursor()`, `move`,
`right_click`, `double_click`, `drag`, `scroll(direction, amount, at=)`, `press(key)`,
`launch`, `focus`, `quit`, `open_url`, `clipboard_read`, `clipboard_write`, `verify`, and the
session lifecycle — `session`, `list_sessions()`, `get_session(id)`, `end_session()`.

The API is synchronous, like the rest of HighhX (there is no event loop in HighhX);
`asyncio.to_thread(driver.click, …)` makes any call awaitable. Coordinates are **desktop
points** in the platform's global space; `screen().scale` converts screenshot pixels to points.

The driver is mechanism, not policy. Inside HighhX it is reached only through the action
executor (risk, approval, audit), the computer runtime (per-element safety) or a command that
asks itself; a program that imports it directly acts as its own user.

## The contract

[`automation/engine/protocol.py`](../src/highhx/automation/engine/protocol.py) is the single
definition of every operation: its arguments and their checks, which protocol version
introduced it, whether it sends keyboard input. `highhx computer protocol` prints it and
[`schemas/computer-protocol.json`](../schemas/computer-protocol.json) is the checked-in copy
(regenerated by `scripts/generate_schemas.py`; a test fails when they differ). The C# engine's
tables are checked against it for the version it implements.

| version 1 (every engine) | version 2 (the Computer Runtime) |
|---|---|
| `status` `frontmost` `launch` `focus` `running` `open_url` `click` (by name) `type` `key` `hotkey` `scroll` `wait` `inspect` `verify` | `capabilities` `screen` `screenshot` `apps` `windows` `window_frame` `quit` `click_at` `move` `cursor` `drag` `element_at` `menu` `clipboard_read` `clipboard_write`; `app` (background delivery) on `type`/`key`/`hotkey`; `x`/`y` on `scroll` |

Version negotiation: the .NET engine is sent its handshake at version 1 and then spoken to at
the version it reports. Operations (or arguments) newer than an engine speaks go to the
built-in engine; with no newer engine available they fail with the structured error
`unsupported` — never silently dropped. Error codes: `invalid_request`, `unknown_op`,
`unsupported`, `unsupported_platform`, `accessibility_denied`, `screen_recording_denied`,
`not_found`, `refused`, `timeout`, `failed`.

## Platforms

Each backend implements what its platform really provides and reports the rest per feature
(`highhx computer status`, `driver.capabilities()`), with the reason and what to install or
grant. An operation a platform cannot perform is an `unsupported_platform` error.

| feature | macOS | Windows | Linux |
|---|---|---|---|
| accessibility tree, element presses | System Events / AX (JXA) | UI Automation (PowerShell, fixed script, `-File`) | AT-SPI (PyGObject, when installed) |
| element at a point | `AXUIElementCopyElementAtPosition` | UIA `FromPoint` | AT-SPI `get_accessible_at_point` |
| pointer: click / double / right, move, drag | CoreGraphics events | `SendInput` | xdotool (X11) |
| wheel scrolling (at a point) | `CGEventCreateScrollWheelEvent2` | `SendInput` wheel | xdotool buttons 4–7 |
| keyboard (foreground) | System Events keystrokes | `SendInput` (Unicode) | xdotool |
| background delivery (`app`) | `CGEventPostToPid` — best effort | `PostMessage` — best effort, keys without modifiers | keyboard only (`--window`, XSendEvent) — best effort |
| windows, bounds, front to back | `CGWindowListCopyWindowInfo` (titles need Screen Recording) | `EnumWindows` (uncloaked, titled) | xdotool |
| move / resize a window | AX `AXPosition` / `AXSize` | `SetWindowPos` | xdotool |
| applications | System Events processes | windows grouped by process | windows grouped by process |
| quit (politely) | Apple event `quit` | `WM_CLOSE` | wmctrl (when installed) |
| menus | System Events menu bar | UIA menu items | AT-SPI menu items |
| screenshot (screen / window) | `screencapture` (needs Screen Recording) | System.Drawing screen copy | grim · ImageMagick · scrot · gnome-screenshot |
| clipboard (text) | NSPasteboard | Get/Set-Clipboard | wl-clipboard · xclip |
| permissions | `AXIsProcessTrusted`, `CGPreflightScreenCaptureAccess` | — | display server, tools present |
| **not available** | — | — | Wayland input (needs the RemoteDesktop portal, not implemented) |

macOS drops synthetic input silently when Accessibility is not granted, so every macOS input
operation checks the grant first and reports `accessibility_denied`. A screenshot without
Screen Recording would show only the desktop: it is refused with `screen_recording_denied`.

**What has run where.** macOS: the native bindings and the read-only operations run against
the real OS in the test suite; real pointer and keyboard input against HighhX's AppKit fixture
runs with `HIGHHX_TEST_DESKTOP_INPUT=1`. Windows and Linux: every backend is tested against
fakes of its OS layer (the arguments it builds, what it refuses); **they have not been run on a
real Windows or Linux desktop in this build.**

## Observation and perception

`driver.observe()` returns the active application and window, all windows, the accessibility
tree (roles, names, states, **bounds**; secure fields are never read) and, only when asked, a
screenshot. A part the platform cannot give is left out, never invented.

Perception ([`computer/perception`](../src/highhx/computer/perception)) is optional:
`ground(driver, "Export PDF")` finds text on screen — the accessibility tree first (exact
names, then partial; several matches are an error, never a guess), then OCR of a screenshot
(tesseract, when installed), converting pixels to points with the display scale. It powers
`computer.click_at` with `text` and `highhx computer click --text`. No model is bundled; a vision
model can be added through the existing `VisionProvider` protocol.

## Safety and approvals

| action | risk floor | who is asked |
|---|---|---|
| `computer.observe` `screenshot` `windows` `apps` `element_at` | low (read) | the agent per approval mode |
| `computer.move` `window` | low | the agent per approval mode |
| `computer.click_at` `drag` `menu` `quit` `clipboard_read` `clipboard_write` | medium | always (a person's own `--yes` counts; the agent never pre-approves) |
| `computer.type` `hotkey` (existing) | medium | always |

- Keyboard input and menu choices never reach a terminal — whether it is in front or named as
  the background target (a menu "Paste" is typing). Shell commands go through `!command`.
- Engines write screenshots only as new `.png` files directly in HighhX's screenshots folder
  (checked by the protocol).
- **HighhX Pro's agent** reaches these operations through `computer_act` (source `desktop`):
  `click_at:X,Y`, `double_click_at`, `right_click_at`, `click_text:TEXT`, `move`, `drag:X1,Y1,X2,Y2`,
  `scroll_at:X,Y,DIRECTION`, `hotkey:KEYS`, `menu:PATH`, `window:X,Y,W,H`, `quit`, `screenshot`,
  `clipboard_read`, `clipboard_write` — each a catalog action run by an executor acting as the
  agent. They are not offered through `run_actions`, because the platform entitles computer use
  by tool name. Desktop observations give the model element positions to aim at.
- Element presses keep the computer runtime's per-element check ("Delete", "Send", "Pay" ask);
  desktop elements also gain double click, right click, hover and drag via their bounds.

## CLI

`highhx computer status` (per-feature capabilities) · `observe --source desktop` ·
`click SELECTOR | --at X,Y | --text TEXT [--right] [--double]` · `scroll DIR [--at X,Y]` ·
`screenshot [--window ID]` · `windows [--app NAME] [--apps]` · `at X,Y` · `move X,Y` ·
`drag X1,Y1 X2,Y2` · `menu APP PATH` · `window APP --frame X,Y,W,H` · `quit APP` ·
`clipboard [--set TEXT]` · `protocol`. See [commands.md](commands.md).

  Cua was used as a reference design. No Cua source file, fixture or model was copied, so no

  HighhX's own.
- No new Python dependency was added: the platform layer uses `ctypes` (standard library) and
  tools the operating system provides or the person installs (reported when missing).

## Limitations

- Windows and Linux backends are implemented and unit-tested against fakes, not run on real
  desktops in this build.
- The C#/.NET engine still speaks protocol 1 (it could not be built here); with it installed,
  version-2 operations run on the built-in engine.
- Background delivery is best effort on every platform (applications may ignore it).
- Linux: no Wayland input; AT-SPI needs PyGObject.
- No sandboxes, cloud computers or VMs; no visible agent cursor; no ONNX perception.
